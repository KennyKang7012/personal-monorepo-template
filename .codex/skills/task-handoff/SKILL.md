# task-handoff — 跨 Session 任務交接

將目前任務整理成可貼到下一個對話的繁體中文交接文件，使用台灣常用詞彙，技術名詞、路徑與識別名稱保留原文。

## 觸發時機

使用者要求「幫我寫交接文件」「寫個 handoff」「換新 Session 繼續」時，針對目前任務產出交接文件；要求「讀取 Handoff.md 接續任務」時，執行接手流程。

這個技能透過文件傳遞任務狀態，不會自動讀取另一個 Session 的私人歷史，也不會建立新聊天、排程或啟動長期目標。

## 交接前核對

1. 確認目標專案與適用的 `AGENTS.md`、README。只讀取目前對話及已授權的相關資料，不補猜無法存取的舊對話內容。
2. 對 Git 專案，確認工作目錄、Git root、目前分支、HEAD commit，以及 staged、unstaged、untracked 檔案；需要時查看相關 diff。非 Git 專案則註明不適用。不要為了產生交接而切換分支、提交或改動程式。
3. 記錄實際執行的驗證命令、工作目錄、exit code 與結果；未執行或僅有舊紀錄的檢查，明確標示。仍在執行的工作另列狀態與可查證位置，不把 Session ID 當成完成證據。
4. 把 Git 狀態放入「關鍵文件和位置」、驗證結果放入「已完成內容」、既有授權與核准界線放入「重要規則和限制」，維持以下八段，不另建平行狀態檔。

## 本 vault 的文件分工

- 先從 `projects/` 或 `experiments/` 的 README 確認專案入口、實作目錄、資料目錄及角色分工；這些位置可能不同。交接時分別記錄相關位置與 Git 狀態，不把 vault 的分支誤當成外部專案的分支，也不為盤點而擴大存取範圍。
- 專案狀態以 README 為入口，長期目標放在 `GOAL.md`，成果與驗證放在 `RESULT.md`，已有 `WORKLOG.md` 則沿用。交接文件只摘要本次接續所需的內容並連結正式紀錄，不取代它們，也不因使用交接技能而自動新增或改寫這些檔案。
- vault 管理工作脈絡，程式與資料維持原位。若要求將交接保存於 vault，預設放在對應的 `projects/<專案>/` 或 `experiments/<實驗>/` 入口目錄；實作目錄的既有交接文件只作來源引用，除非另外授權更新。
- 「重要規則和限制」須保留不同 Agent 的分工與當次核准界線；「建議下一步」中的日期、排程與待執行動作，不代表已授權重試、啟動自動化或接管另一個 Agent 的工作。

## 輸出結構（固定八段，缺一不可）

1. **目前任務目標**
2. **已完成內容**
3. **關鍵文件和位置**（路徑、連結，越具體越好）
4. **重要規則和限制**（安全守則、使用者明確交代不能做的事、環境限制）
5. **已確認結論**（使用者已經拍板、驗證過的決定）
6. **待確認事項**（還沒拍板、還沒驗證的，一律列在這裡，不要混進「已確認結論」）
7. **不要重複做的事情**（已經試過失敗、已經排除的方案，明確寫出來避免下一個任務重踩）
8. **建議下一步**

## 寫作規則

- **只保留對下一步有用的資訊**——這是最高原則，其他規則都是這條的具體化
- **刪除過程性閒聊**：不要記錄「使用者說了什麼玩笑話」「來回確認了幾次」這種對話流水帳，只留結論
- **刪除舊報錯**：已經修好、已經是死路的錯誤訊息不用整段貼進去，除非它本身就是「不要重複做的事情」的證據，這種情況只留一行摘要（症狀 + 為什麼是死路），不用貼完整 log/traceback
- **刪除臨時方案**：中途試過但後來被更好方案取代的做法不用寫，除非該臨時方案本身有值得警惕的坑（一樣併入「不要重複做的事情」）
- **不確定的資訊一律標「待確認」**：沒有本人明確拍板、只是推測或還沒驗證的內容，前面加註「（待確認）」，不要包裝成確定的事實。這條優先於「精簡」——寧可多一句「待確認」的提醒，也不要漏掉一個不確定性讓下一個任務誤判

## 使用方式

1. 掃描目前對話/session 裡跟這個任務相關的內容（做了什麼、決定了什麼、還卡在哪、使用者交代過的限制）
2. 依照上面八段結構整理，套用寫作規則過濾
3. 輸出成 Markdown，不用額外的 frontmatter 或包裝，直接是能貼到下一個任務開頭的內容。沒有內容的段落寫「無」，需要資訊才能判斷的段落寫「待確認」，不要猜測補齊
4. 如果使用者有指定要存成檔案，才寫檔；沒指定就直接在對話裡輸出文字內容，不要自作主張建立檔案

### 寫入檔案與新 Session 提示詞

- 依使用者指定位置保存；只說要存成交接檔而未指定路徑時，先依專案 README 確認維護位置與既有檔案，沿用 `Handoff.md`、`HANDOFF.md` 等原有大小寫，不建立只差大小寫的副本。無既有約定時才新增 `Handoff.md`；vault 內的專案入口依上節選擇。不要將不同專案的任務混寫在 vault 根目錄。
- 更新前先讀取既有交接文件，保留仍有效的限制與未完成事項；若內容屬於另一項任務且會被覆蓋，先確認目的地。遵守目的地的 Markdown 規範；本 vault 的 Markdown 檔案需有 `last_edited` frontmatter，前述「不加 frontmatter」只適用於聊天中的交接文字。
- 不保存 API Key、密碼、Token、個資或原始私人 Session 歷史；只保留對接續必要且可保存的摘要。
- 在交接檔標示紀錄時間與時區；歷史查核、當次實測及待執行工作分開標示。檔案連結須可從交接檔位置解析，外部本機目錄使用完整路徑；保存後核對連結與八段內容，不能只確認寫檔成功。
- 完成交接後，另附可貼到新 Session 的提示詞，填入實際專案與交接檔完整路徑，不留下佔位符。要求先讀適用規則與交接檔、核對現況、回報差異，再依已確認授權接續。

## 新 Session 接手流程

1. 先讀目標專案適用的 `AGENTS.md`、README 與指定交接檔；未指定時優先依 README 的交接路徑尋找，並辨識原有檔名大小寫。有多份且無法判斷用途時先釐清，不自行挑選。找不到時明確說明缺少什麼，不假稱已取得上個 Session 的上下文。
2. 核對交接提及的關鍵檔案、Git root、分支、HEAD 與未提交變更。交接檔是先前快照；以使用者最新指示、適用規則與實際觀察更新判斷，遇到影響目標或授權的衝突時先釐清。
3. 區分先前驗證紀錄與本次重新驗證。不要因為舊紀錄寫「通過」就宣稱目前仍通過；依任務授權執行必要且相關的驗證，外部操作或需另行核准的重試仍依原限制處理。
4. 簡短回報目前進度、差異、未驗證項目與下一個最小步驟。使用者已要求接續且授權明確時，繼續完成範圍內工作；只要求閱讀或分析時，不進入修改。
5. 交接檔中的建議下一步不是新增授權。不得自動擴大階段、覆蓋既有變更，或執行未獲授權的 push、merge、部署及其他外部操作。

## 來源
